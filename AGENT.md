## Current milestone

The scaffold and authentication foundation are on `develop`, including PAT and bearer authentication, browser sign-in, username/password login, account profiles, and PAT management. The active `dev/feat/identity-users-groups` increment adds typed user-directory and group operations with lazy paging, role-bearing membership, Oasis extension mappings, and worked documentation examples. The SDK exposes a synchronous `NomadClient`, `Scope`, and Identity operation groups through `client.identity`.

**Deployment terminology.** NOMAD Central is the public NOMAD deployment hosted by FAIRmat. A self-hosted NOMAD Oasis runs the same platform on an organization's infrastructure. The credential selects the deployment for authentication and API requests. Omit its `endpoint` for Central, or set the full HTTPS API v1 URL for an Oasis, development, or test deployment. Move any existing `NomadClient(endpoint=...)` setting to its credential.

- **Bearer credentials.** `BearerTokenCredential` accepts an existing NOMAD PAT or Keycloak access token. A scoped PAT is the documented option for unattended jobs, remote kernels, and CI. The caller replaces expired or rotated bearer tokens.
- **Browser credentials.** `BrowserCredential` accepts an explicit Keycloak issuer and public client ID, plus both authorization and token endpoints or opt-in OIDC discovery. An optional caller-supplied provider alias goes to Keycloak as `kc_idp_hint`. Central's verified institutional alias is `helmholtz-aai`. A self-hosted Oasis may use Central's realm or its own Keycloak, including an institutional provider configured behind it.
- **Browser lifecycle.** The first permitted request opens the system browser. An explicit `authenticate()` starts a fresh sign-in. Use Authorization Code with PKCE S256, a loopback callback, and in-memory access and refresh tokens. Refresh on demand near expiry, share one refresh across concurrent requests, and keep rotated refresh tokens. Reauthentication is explicit. Closing a client releases its API connection pool while the caller can still reuse the credential on the same deployment.
- **Password credentials.** `PasswordCredential` accepts an explicit username and password or reads `NOMAD_USERNAME` and `NOMAD_PASSWORD`. It uses the deployment's legacy `POST /auth/token` route and repeats the password exchange near expiry. The pair stays in memory for the credential's lifetime. A rejected login blocks automatic attempts until explicit authentication or credential replacement.
- **Scope and verification.** `allowed_scopes` is an immutable local policy. NOMAD enforces token permissions. The milestone passed offline and live PAT CI. The browser flow has offline coverage and a live Central no-login callback probe. A completed browser sign-in and a live username/password login each need separate manual acceptance. Test a self-hosted Oasis when an authorized deployment is available.
- **Users and groups.** `client.identity.users` supports exact lookups, ordered batch resolution, prefix search, and invitations. `client.identity.groups` supports typed create, read, list, update, membership replacement, and deletion. NOMAD assigns the signed-in creator as the sole owner. Creating role-bearing membership reads `/users/me` to construct the required owner record. Group ownership transfer is outside the verified NOMAD contract. Offline tests and strict documentation builds pass. Live group writes and invitations remain pending because they change deployment state.

The PyPI distribution is `nomad-python-api` and the import package is `nomad_python_api`. This SDK covers NOMAD's core data, app, and platform operations. Workflow authoring, workflow YAML generation, and orchestration belong to the separate planned `nomad-workflow` library. Use `nomad-utility-workflows` as a reference for core API use cases. [Existing NOMAD utilities](https://github.com/FAIRmat-NFDI/nomad-utility-workflows)

## Approval gates

1. **Plan.** Inspect the working tree, current tests, and upstream contract. Compare viable approaches when there is a material tradeoff. Cover affected areas, acceptance criteria, tests, docs, diagrams, and security. Wait for explicit scope approval before editing.
2. **Develop and test.** Keep one logical increment and preserve unrelated changes. Aim for about 200 changed lines excluding docs and tests. Report checks, failures, and exact manual test steps. Obtain the maintainer's manual test result or explicit waiver. Behavior changes after review require fresh sign-off.
3. **Commit.** Update the Unreleased changelog when one exists and applies. Rerun the relevant checks, report missing verification, and propose a Conventional Commit. Commit only after manual sign-off or waiver and explicit commit approval. The maintainer may give both together. Stage the reviewed files and report the commit hash.

Get explicit authorization for CI, release, license, or dependency changes and before pushing, tagging, publishing, or opening a PR. Keep required checks enabled. Breaking changes require explicit approval, a Conventional Commit `!`, and a `BREAKING CHANGE:` footer.

## Architecture and code quality

- Follow the Azure SDK pattern of client, operation groups, and a shared request pipeline. Use boto3's resource pattern where typed domain models benefit. Keep HTTPX, raw responses, generated wire types, and Graph request payloads internal. [Azure SDK design](https://azure.github.io/azure-sdk/python_design.html) · [boto3 resources](https://boto3.amazonaws.com/v1/documentation/api/latest/guide/resources.html)
- Keep dependency direction from public client and models to operations, protocol, and core. Keep schema interpretation independent of transport. Models reuse their client's HTTP session. Representations, equality, and serialization avoid network access. Document any lazy I/O and the ownership, deadlines, and cleanup of background work.
- Register the method, path, and required scopes beside each operation. Default to REST. Verify the target deployment's OpenAPI or Graph contract before adding features. Use Graph for nested reads, references, or projections where it reduces request count or response size. Keep any approved code generation internal and record its inputs. [NOMAD OpenAPI](https://nomad-lab.eu/prod/v1/api/v1/openapi.json) · [NOMAD Graph API](https://docs.nomad-lab.eu/howto/manage/program/graph_api.html)
- Pass deployment settings through explicit keyword-only arguments. Keep provider aliases and wire-specific options caller-supplied. Where an operation supports Oasis extensions, use explicit mappings such as `extra_query`, `extra_json`, or multipart fields. Keep method, destination, auth, and named request fields under SDK control. If a mapping field becomes a named option, retain the mapping and reject duplicate values.
- Use SDK-owned, keyword-only settings for pool limits and phase timeouts. Keep defaults compatible, enforce finite resource bounds, and distinguish an unsent pool timeout from a failure after sending. Design bulk data operations for bounded-memory streaming and independently controlled inactivity and overall deadlines.
- Keep transport internals private. The explicit `http_client` option accepts a trusted, caller-owned synchronous HTTPX client. The caller owns its TLS settings and hooks. Borrowed HTTP clients and `NomadTransport` pools stay open when a NOMAD client closes. Keep endpoint binding, scope checks, request authentication, and redirect handling in the shared pipeline.
- Use straightforward typed Python and descriptive names. Keep private modules underscored and public exports explicit. Use `begin_*` for long-running operations, `list_*` for paged results, and `get_*` for individual resources. Put public errors in `exceptions.py`, redact unsafe causes, and use logging for library diagnostics. Keep sync and async logic shared where practical. Deprecate with `DeprecationWarning`, a changelog entry, and removal in a major release.
- The current stack is Python 3.10+, uv, Hatchling, HTTPX, pytest, and MkDocs Material. Propose additions with their purpose, license, maintenance, provenance, and dependency risk. Prefer the standard library or an existing dependency. Keep heavy data and unit integrations in optional extras. Ruff, strict typing, coverage, and security scanning apply as their tooling is approved and configured. The draft Apache-2.0 license requires maintainer approval.

## Security requirements

- **Identity and data.** Bind credentials and caches to the intended deployment and authorization context. Use least privilege and enforce token expiry. Treat the service as authoritative for permissions. Require explicit calls for destructive or publishing actions. Keep secrets and private payloads out of logs, error details, examples, fixtures, telemetry, and disk caches. Keep `.env` ignored. Redact signed URLs, headers, and query parameters. Default examples to read-only operations.
- **Network.** Verify HTTPS certificates and hostnames and provide explicit private CA configuration. Reserve plaintext for explicit loopback cases. Validate scheme, host, and port, reject embedded credentials, and validate server-supplied destinations before use. Keep redirects disabled unless the operation needs them. Cross-origin transfers require explicit destination rules and carry no NOMAD credentials. For caller-influenced destinations in a server integration, use an administrator allowlist and connection-time egress controls that also cover DNS changes and redirects. Exclude metadata, link-local, and loopback destinations except for an authorized local flow or isolated test. [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Browser auth.** Require PKCE S256 and per-attempt state. Bind the listener to the configured loopback path and port and close it on every exit path. Validate issuer metadata and the identity endpoint origin. Keep cookies in the browser. For future cookie-authenticated integrations, enforce origin checks and CSRF protection on state-changing requests, use appropriate cookie flags, and configure credentialed CORS explicitly.
- **Inputs and files.** Validate and bound input at trust boundaries. Use structured HTTP parameters and payloads. Keep untrusted values out of shell commands, evaluated templates, and unsafe deserialization. Constrain file access, reject archive traversal and unsupported special files, bound counts and sizes, stream large transfers, and clean up partial files. Opt in before overwriting.
- **Reliability.** Bound connection and I/O waits, total operation deadlines, response sizes, polling, concurrency, and graph/query complexity. Honor valid `Retry-After` within the operation budget for eligible retries. Use bounded backoff with jitter where applicable. Replay mutations only with documented idempotency or verified state. Test the controls that a change relies on. [OWASP API security risks](https://owasp.org/API-Security/)
- **CI.** Lock dependencies with uv, review material transitive dependencies and applicable advisories, and record any approved exception with its rationale and review date. Give workflows minimum permissions, pin third-party actions by full SHA, and isolate privileged jobs and secrets from PR code. [GitHub Actions security guidance](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)

## Docs, testing, and release

- Publish the Usage and Developer guides together with the shared FAIRmat theme and header selector. `mkdocs.yml` builds the local preview. `mkdocs.public.yml` builds `site/public/` for Pages. Keep private material under `docs/internal/`, excluded from public builds. Record the theme source revision in `docs/theme/README.md`. [FAIRmat docs source](https://github.com/FAIRmat-NFDI/nomad-docs)
- For every new public feature, include a worked example with prerequisites, runnable Python, and an expected result. Put the code in `tests/snippets/` and include its marked source in the user guide and relevant Python API reference. Reuse the same snippet across pages and keep assertions and mocks outside it. Document each REST route, request fields, responses, errors, and SDK mapping. Update the Developer guide and relevant Mermaid component, sequence, state, or ER diagrams for major changes. [Developer guide](docs/dev/index.md) · [Identity architecture](docs/dev/identity/index.md)
- Run the offline tests, both strict docs builds, and the build and offline wheel import checks. The current CI also checks built docs assets. If coverage tooling is introduced, target at least 90% coverage for new code. Keep browser interactivity in manual acceptance. Use the existing `integration` marker for the read-only live PAT suite.
- CI runs package and docs checks on PRs to `develop` and `main`. On trusted pushes to those branches, it also runs live PAT checks using `nomad-test`, with `NOMAD_TEST_API_URL` as an environment variable and `NOMAD_TEST_PAT` as an environment secret. The token must be issued by that exact deployment. Additional live test targets require authorization.
- Branch from `develop` as `dev/<name>` and open a PR back to `develop`. After checks pass, a push to `develop` publishes both guides to GitHub Pages. Promote reviewed `develop` to `main` by PR, with a package version bump. A passing push to `main` publishes to PyPI via Trusted Publishing. The initial scaffold was the direct-commit exception for `main`. [Branches and deployment](docs/dev/deployment.md)

```sh
uv lock --check
uv sync --locked --group docs
uv run --offline --no-sync python -m pytest tests/unit tests/snippets
uv run --no-sync mkdocs build --strict -f mkdocs.yml
uv run --no-sync mkdocs build --strict -f mkdocs.public.yml
uv build
uv run --no-sync --env-file .env python -m pytest -m integration tests/integration
```

## Future increments

Each increment needs scope approval. Finish core capabilities as needed, then prioritize uploads, entries and archives, queries and bulk data operations, and other core resources. Compatibility shims, async parity, and CLI work follow separate approval.

- Use explicit upload lifecycle states, documented idempotency, and dirty tracking for edits. Expose paging and long-running operations through typed iteration and bounded pollers.
- Design archive and schema access for lazy loading and streaming. Collect nested reads and references to avoid N+1 queries. Scope any approved cache by deployment, API version, and authorization context, with bounded size, TTL, and invalidation. Keep credentials and private content out of persistent caches.
